## Context

The Préstamos tab was reading `GET /api/liabilities` and the only generated loan
UI was the shared consult terminal. The backend already has the machinery this
feature needs: a `generated_ui` table storing a `{{placeholder}}` template plus a
snapshot descriptor, `persist_ui`/`hydrate_ui`, `hydration/placeholders.py`, a
deterministic `engine/audience.classify`, and a research provider (Gemini
grounding + static fallback). This change wires a **per-loan** surface on top of
that machinery rather than inventing a new one.

## Goals / Non-Goals

**Goals:**
- Created loans appear in the Préstamos tab alongside active liabilities; the
  manual application form creates a real loan.
- Opening a loan lazily builds (once) a page for that user+loan and re-hydrates it
  on later visits — no stale values stored in the template.
- The page is personalized deterministically: emoji/color for `simple` users,
  denser/technical as financial activity rises.
- The stated purpose grounds the page in web research; a private reason skips
  research but keeps personalization.

**Non-Goals:**
- Changing the consult terminal (`loans_credits`) or the La Mesa / El Revés flows.
- Auth/ownership beyond verifying the loan belongs to the user.
- Editing a stored template by hand; it is only replaced by regenerating.

## Decisions

**1. Server-side unified list, not two client calls.** The router calls the
existing `get_liabilities` MCP tool plus a new `list_loans` tool and tags each row
`source`. One endpoint, one client list, still MCP-only data (INV-014).

**2. `loan_detail` is a new `generated_ui` domain keyed by `loans.id`.** Reuses
`persist_ui`/`hydrate_ui`; a new `find_surface(user, domain, entity)` locates the
stored template for lazy reuse. Distinct from `loans_credits` so the consult
terminal is untouched.

**3. Live loan context at hydration.** `_render` merges a domain-specific
`loan_context` (the `loans` row + a schedule regenerated by `engine/terms_for`)
after the snapshot, so placeholders/bindings resolve to fresh values (INV-015,
INV-022). Research costs are external reference data and ride the snapshot.

**4. Deterministic personalization first.** `get_audience` decides the directive
before the LLM writes a line; `activityScore` blends comprehension and real
activity so density scales beyond three coarse buckets. For `simple`, `persist_ui`
pins `amitie.voz-color.v1` even without an accessibility profile, so those users
always get the emoji/color catalog.

**5. Research is a provider, not a tool.** The provider layer already holds the
grounding chain; `LoanDetailService` calls `research_topic` directly (as the LLM
provider is called directly), while all *data* stays behind MCP. `purpose_private`
short-circuits before the call.

**6. Purpose is resolved server-side on create.** `POST /api/loans` reads the
`loan_requests` state for `purpose`/`purpose_private` when the client did not send
them, so the trust boundary stays on the server.

## Risks / Trade-offs

- **[Risk]** Grounding latency/failure. → Strict timeout + broad static fallback;
  on failure the page still generates from the user's own data.
- **[Risk]** Extra LLM call on first open. → It happens once per loan; later opens
  only hydrate.
- **[Risk]** `simple` audience now switches many surfaces to `voz-color`. →
  Intended (accessibility), and it reuses the existing catalog/registry contract.
- **[Risk]** Generated components could hardcode a value. → Prompt forbids it and
  the persisted template is bindings/placeholders; hydration keeps live values
  for known keys.
